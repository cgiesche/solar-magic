# What blocks look like is no input of what they do

Probes (CONTEXT.md) stay valid as long as the ROM bytes they read are unchanged. The emulated game also reads what it only draws: the Map16 tiles' quarters (boot, the probe level, a block changing into another tile) and the colors (every level load uploads the palettes). Those bytes lie on pages that the title screen and the probe level read, so drawing a Map16 tile of the shared pages, or changing a shared color, dropped every block, collision and sprite probe in every tileset, and the probe worker learned them all again (about 512 tiles and 200 sprites per tileset), although only acts-like and the blocks' code can change behavior.

We decided that the probe worker (core/probehost.ts) does not record reads of display data, as it already did for GFX file data and ExAnimation data: the FG Map16 quarters (tiles 000–1FF where each tileset's pointers lead, learned by emulation as for the tileset sharing; the extended tiles' table), the BG Map16 quarters, the shared palettes and the levels' own palettes with their pointers (core/gfxpages.ts, gfxDisplaySkipMask). Acts-like, the custom block table and code, patches and the game's code stay what they read, so changing them still drops the results that read them, found by emulation as before. The worker's other results (object kinds, level scans, the camera at a place) leave the display data out as well: none of them is a picture. Since the result learner's jobs run in the worker too (#175: the sprite images first; #177: the levels' uses, the sprite memory check, the animated tiles and colors; #178: the layer 3 kinds, the tiles of the level as edited; #179: the object thumbnails, the placement preview, the jump arcs, the layer 2 motions, the overworld path kinds, the prefab suggestions, the object boxes for resizing; #183: the overworld's maps at an event progress, the submaps' views and the overworld sprites' images; #233: the levels' game BGs for the remap preview, a prefab's places, the loads comparing a broken up prefab, the slippery entrance actions and the object tables, all no pictures), each kind of job says there whether it is a picture (core/probeprotocol.ts LEARN_KINDS), as on the main thread; the pictures run from a boot snapshot of their own there that counts the display data. The overworld's jobs run on the overworld's own emulator, which has no skip mask (as on the main thread before): they count the display data, the submaps' views too, though they are no picture.

On the main thread the result learner (core/learner.ts; what is needed at once, and without a worker the probe host's jobs) does the same per result: each job says whether it is a picture. Those that are not (without a worker the worker's jobs that are none; the object tables and slippery entrance actions were learned here until #233) leave the display data out, and run from a boot snapshot whose reads leave it out too (booted on an emulator of the learner's own: the title screen reads tiles and colors, which every result counts). The tilesets' pointers are no picture either, but that boot snapshot's mask needs them, so they run from the main emulator's boot snapshot, and their reads leave out the display data by themselves (a first load finds where the tile data is) and not on top of the boot's reads. Pictures (without a worker the worker's pictures; before #233 also loads at once, as a level's BG for the remap preview) keep it and run from the main emulator's boot snapshot. So the choice is made by the result, not by the emulator. Where the tables lie is the ROM layout the editor already writes them by (the vanilla BG table and shared palettes, the extended tables and level palettes by their patches' pointers); which tile data a tileset uses is learned by emulation.

## Considered options

- Probing again only when acts-like changes: rejected. It is an SMW rule written into the editor instead of what the emulation reads: a GPS block with new code and the same acts-like would keep its old result.
- Recording the Map16 tables by byte instead of by page: rejected, it only helps partly. The title screen's tiles are read at boot, which every result counts, so drawing those would still drop everything.
- Leaving out the display data for every emulated result: rejected. Object thumbnails and sprite images show the tiles and colors; only the results that are no pictures leave it out (the probe worker's all, the result learner's by job).

## Consequences

Drawing tiles and changing colors keep the behavior shown; a block's result is learned again only when what it does may have changed. A custom block whose code reads Map16 quarters or colors and acts on them would keep a stale result after such an edit; no such block is known. The worker learns the tilesets' pointers once (about 0.75 s on its first probe of a session; kept in the result cache with the bytes they read, which leave out the tile data and the colors). The result learner uses the same pointers (the same cache entries) and boots a second time for its results that are no pictures (about 0.1 s, at their first job and again after a change of what the boot read, a display edit included: its state holds the title screen's colors); drawing a tile or changing a color then drops the pictures only, not the levels' uses (before: the uses of half or all of the levels, each a level load to learn again).

The palette tab's trace of where the level's colors are loaded from (core/colorsources.ts) leaves out the colors' values only (gfxFileColorValueSkipMask, a part of gfxDisplaySkipMask; it keeps the ExAnimation data, as a color animation writes colors too): the own palettes' pointers say where the colors come from, so setting or removing a level's own palette traces again, changing a color doesn't. It runs from an own boot snapshot that leaves them out too, as the result learner's.
